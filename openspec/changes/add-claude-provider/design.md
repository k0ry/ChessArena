## Context

Мотивация описана в proposal.md (Why). Текущее состояние, важное для подхода:

- Провайдер выбирается через `NeuralProvider` и `PlayerConfiguration`; комментатор использует ту же конфигурацию, что и игроки, поэтому ведущий получает Claude тем же путём.
- `Seat` несёт `ChatRoute` (`http`, `geminiCLI`), а `ArenaChatTransport` диспетчеризует вызов по маршруту и хосту адреса. HTTP-ветка формирует запрос в формате OpenAI Chat Completions и читает `choices[0].message.content`.
- Ошибки сводятся к `APIErrorReason` по кодам OpenAI; в UI попадают только известные категории, тексты провайдера не показываются.
- Ключи xAI и OpenAI лежат в Keychain (`com.chessarena.broadcast`) и передаются позиционно через `seat(side:grokKey:chatKey:)` в пяти местах `MatchRuntime`.
- Тайм-ауты: игрок 10 минут, ведущий 90 секунд с резервной репликой. Движок уже автоматически повторяет сетевые ошибки с нарастающей задержкой и ставит партию на паузу при ошибках ключа и квоты.
- Приложение на Swift без внешних зависимостей; официального Swift SDK Anthropic нет, поэтому используется сырой HTTP через `URLSession`, как для остальных провайдеров.
- Change `add-gemini-subscription` не завершён и редактирует `PlayerConfiguration`, `ControlView`, `MatchRuntime`.

## Goals / Non-Goals

**Goals:**

- Один новый провайдер в enum, один новый маршрут транспорта, одна новая панель подключения; остальной код игры не замечает разницы между провайдерами.
- Полная обработка контракта Messages API: заголовки, формат `system`/`messages`, блоки `content`, `stop_reason`, типы ошибок.
- Каталог моделей аккаунта без зашитого списка, с ручным вводом как запасным вариантом.
- Тесты без обращения к сети, по образцу существующих `MiniHTTPServer`-тестов.

**Non-Goals:**

- Доступ по подписке Claude через локальный Claude Code CLI или OAuth. Отдельный change.
- Стриминг ответа. Текущий движок ждёт полный ответ и не показывает частичный текст.
- Structured outputs или инструменты для хода. Игрок продолжает возвращать JSON в тексте, как остальные провайдеры.
- Серверный fallback на другую модель при отказе. Противоречит принципу приложения: выбранная модель не подменяется скрыто.
- Кэширование промпта. Запросы короткие, выгода отсутствует.

## Decisions

### 1. Отдельный маршрут `anthropic`, а не ещё один `baseURL` для HTTP-ветки

`ChatRoute` получает `case anthropic`. `ArenaChatTransport` при этом маршруте вызывает новый `AnthropicTransport` (отдельный тип в `ChessArenaCore`, реализует `ChatTransport`). Альтернатива: расширить `URLSessionChatTransport` условиями по хосту. Отвергнута: различаются заголовки (`x-api-key`, `anthropic-version`), форма тела (`system` отдельным полем, `max_tokens` обязателен), форма ответа и ошибки. Ветвление внутри одного транспорта смешало бы два контракта и усложнило тесты.

Адрес по умолчанию для провайдера: `https://api.anthropic.com/v1`; `Seat.completionsURL` для этого маршрута даёт `<base>/messages`.

### 2. Форма запроса

```
POST /v1/messages
x-api-key: <ключ>
anthropic-version: 2023-06-01
content-type: application/json

{
  "model": "<id>",
  "max_tokens": <по роли>,
  "system": "<call.system>",
  "messages": <call.inputMessages>,   // те же user-сообщения, что у других маршрутов
  "output_config": { "effort": "<по роли>" }
}
```

- Параметр `thinking` не передаётся. На актуальных моделях 5.x мышление включено по умолчанию и его явное отключение возвращает 400; на более старых моделях его отсутствие означает обычный ответ. Отсутствие параметра — единственный вариант, корректный для всего каталога.
- `effort`: `high` для хода и для послематчевого совета, `low` для реплик комментатора. Глубина передаётся через `ChatCall` новым полем роли или напрямую выбирается транспортом по `call.url`/контексту; предпочтительно явное поле `ChatCall.effort: String?`, которое другие маршруты игнорируют.
- `max_tokens`: токены рассуждения входят в лимит. Игрок: 16000, ведущий: 2048. Ответ со `stop_reason == "max_tokens"` считается нечитаемым (попытка потрачена, позиция не меняется).
- Prefill ассистента не используется: на моделях 4.6+ он возвращает 400.

### 3. Разбор ответа

Текст ответа — конкатенация блоков `content[].type == "text"`. Блоки `thinking` и `redacted_thinking` отбрасываются: они не попадают ни в парсер хода, ни в эфир, ни в журнал как реплика (в журнал моделей попадает только итоговый текст, как у других провайдеров).

`stop_reason`:

- `end_turn` — нормальный ответ.
- `max_tokens` — `ChatError.unreadable`.
- `refusal` — новая категория `APIErrorReason.refusal`, см. решение 4. HTTP-статус при этом 200, поэтому проверка `stop_reason` обязательна до чтения `content`.
- иные значения (`tool_use`, `pause_turn`) невозможны без инструментов и трактуются как `unreadable`.

### 4. Классификация ошибок Anthropic

Вторая таблица рядом с существующей `APIErrorReason.classify`, выбирается по маршруту:

| Ответ Anthropic | Категория |
|---|---|
| 401 `authentication_error` | `.authentication` |
| 403 `permission_error` | `.permission` |
| 404 `not_found_error` | `.modelAccess` |
| 400 `invalid_request_error`, сообщение о недостатке кредитов (`credit balance`) | `.quota` |
| 400 `invalid_request_error` иное, 413 `request_too_large` | `.request` |
| 429 `rate_limit_error` | `.rateLimit` |
| 500 `api_error`, 529 `overloaded_error` | `.server` |
| 200, `stop_reason == "refusal"` | `.refusal` (новая) |

`.refusal` получает собственный текст для UI и ведёт себя как ошибка доступа: партия встаёт на паузу без автоматического повтора, потому что повтор того же запроса даст тот же результат. Тексты ошибок провайдера в UI не попадают (могут содержать ключ или идентификатор запроса).

### 5. Каталог моделей через Models API

Новый `ClaudeConnection` (`@MainActor ObservableObject`, по образцу `GeminiConnection`): `models`, `busy`, `status`, `refresh(key:)`. Запрос `GET /v1/models` с теми же заголовками, постраничный обход по `has_more`/`last_id` (`after_id`), фильтр `id` с префиксом `claude-`, сортировка по `created_at` по убыванию, отображение `display_name`.

Каталог — удобство выбора, а не подтверждение доступа: модель из списка может быть недоступна аккаунту, и это проявится ошибкой `.modelAccess` при первом запросе с паузой партии. Это соответствует существующей политике для Gemini. Ручной ввод ID сохраняется для моделей, которых в каталоге нет.

Альтернатива: зашитый список моделей. Отвергнута: устаревает и не отражает права аккаунта.

Модель по умолчанию `claude-opus-5-5` задаётся в `ModelCatalog` с комментарием о дате, как для Grok и ChatGPT.

### 6. Ключ и его передача

Keychain-аккаунт `anthropic` в существующем сервисе. Позиционные параметры `seat(side:grokKey:chatKey:)` заменяются структурой `ProviderKeys { grok, chatGPT, anthropic }`, чтобы пять мест вызова в `MatchRuntime` не росли на параметр с каждым провайдером. `GameMemory.remember` и `ModelLog.sanitize` уже получают список `apiKey` всех мест, поэтому ключ Claude скрывается в журнале и памяти автоматически.

### 7. Интерфейс

- В `PlayerPanel` провайдер Claude доступен всем трём участникам. При выборе Claude показывается `Picker` с каталогом (как для ChatGPT через вход) и строка «каталог не загружен» с текущим ID, если модель отсутствует в списке; рядом текстовое поле для ручного ID.
- `ClaudePanel` появляется, когда `needsClaude`: `SecureField` ключа, кнопка «Обновить модели», статус подключения. Смена ключа сбрасывает каталог.
- Валидация перед стартом и продолжением: ключ не пустой, модель не пустая. Тестовый ход не требуется.
- Блокировка настроек во время активного хода и возможность смены модели на паузе наследуются от существующих правил `PlayerPanel`.

### 8. Сетевой журнал

`NetworkTrace` получает вид `.anthropicMessages` и `.anthropicModels`, чтобы «Log сети» различал запросы к Anthropic. Авторизационные заголовки, как и сейчас, не записываются.

### 9. Тесты

- `AnthropicTransportTests` на `MiniHTTPServer`: заголовки и тело запроса, разбор `content` с блоком `thinking` перед текстом, `stop_reason` `max_tokens` и `refusal`, таблица ошибок из решения 4 с секретом в сообщении, который не должен попасть в `userMessage`.
- `ClaudeConnectionTests`: постраничный каталог, фильтр префикса, сортировка, ошибка ключа.
- `PlayerTests`: `PlayerConfiguration(provider: .claude).seat(...)` даёт маршрут `anthropic`, нужный ключ и ни одного чужого ключа; `ProviderKeys` для существующих провайдеров не меняет поведение.
- `MatchTests`: ведущий Claude даёт реплику в срок; при `.refusal` игрока партия на паузе без автоповтора.
- Сохранение: `SavedSession` с `hostProvider = .claude` проходит round-trip; старый файл без Claude открывается.

## Risks / Trade-offs

- [Старые модели могут отклонить `output_config.effort`] → ошибка показывается как `.request`; каталог по умолчанию показывает актуальные модели первыми. При необходимости позже можно фильтровать по полю `capabilities` из Models API.
- [Токены рассуждения съедают `max_tokens` игрока на сложных позициях] → лимит 16000 и трактовка `max_tokens` как потраченной попытки, а не как зависания; при повторяемости снизить `effort` игрока до `medium` настройкой по умолчанию.
- [Комментатор не укладывается в 90 секунд при `effort: low`] → существующая резервная реплика ведущего срабатывает по тайм-ауту; задача живой проверки измеряет фактическую длительность.
- [Одновременные правки с `add-gemini-subscription`] → реализация начинается после завершения или заморозки того change; порядок зафиксирован в proposal.md.
- [Пользователь вводит ключ другого сервиса или ключ с ограниченными правами] → 401/403 классифицируются и останавливают партию с понятной причиной; ключ не выводится.
- [Ключ в URL или теле запроса в журнале] → ключ передаётся только заголовком `x-api-key`; заголовки не журналируются.

## Migration Plan

Изменение добавляет провайдера и не меняет схему `SavedSession`: `NeuralProvider` кодируется raw value, новое значение `Claude` читается только новыми версиями, а старые файлы без него открываются без изменений. Откат — удаление провайдера из enum; файл сессии с `Claude` в этом случае не декодируется, и приложение поведёт себя как при повреждённом файле (копия сохраняется, настройки сбрасываются). Это допустимо для локального приложения одного пользователя.

## Open Questions

- Нужна ли настройка `effort` в UI (например, для игрока `medium`/`high`), или фиксированных значений по ролям достаточно. Можно решить после живой проверки длительности ходов.
- Стоит ли ограничивать каталог по `capabilities` Models API, когда поле станет стабильным для всех моделей.
