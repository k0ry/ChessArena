# План: согласованные тайм-ауты LLM и работающий автоповтор

Дата: 19 октября 2026. Статус: реализация, тесты и сборка завершены; визуальная проверка остаётся открытой из-за недоступности UI-инструмента. Результаты: [verification.md](verification.md).

Предыдущие tasks/plan.md, tasks/todo.md и результаты исправления счёта сохранены без изменений. Этот план относится к новому обращению о двухминутном ограничении и ложной надписи автоповтора.

## Подтверждённая причина

1. `Sources/ChessArenaCore/MatchEngine.swift:257–258,690–708`: отсчёт строится от `requestTimeout`, по умолчанию 600 секунд; внешний `RequestDeadline` получает этот же бюджет. Но `Sources/ChessArenaCore/GeminiCLI.swift:189` запускает Antigravity с `--print-timeout 120s` и ограничением процесса 125 секунд. Вызов Gemini завершается существенно раньше обещанного интерфейсом срока. Простое увеличение внешнего таймера ничего не исправит.
2. `Sources/ChessArenaCore/Chat.swift:132–138`: все `.cli` и `.claudeCLI` считаются требующими ручного вмешательства, включая `.timeout`. `MatchEngine.stall` поэтому сразу оставляет `retryAt=nil`. Это политика классификации ошибок, а не зависший планировщик: `MatchRuntime.tick()` вызывает `engine.advance` и во время паузы.
3. `Sources/ChessArena/ProgramView.swift:89–94`: любой `pausedPlayer` выводит «ПОВТОР ЗАПРОСА / Повторяем автоматически…», независимо от наличия запланированного повтора. `BroadcastPicture` не передаёт экрану различие автоматического ожидания и ручной паузы. В `MatchRuntime.swift:562` также есть недостоверный запасной текст.
4. `GeminiCLI.complete` имеет собственный цикл из двух попыток на `.execution`, помимо повторов движка. Он скрывает часть попыток от общего счётчика и усложняет согласование времени.

### Подтверждение журналом

Снимок на момент проверки: Gemini `gemini-4-argon-high` белыми против LC0 чёрными; 17 событий `paused` с причиной `gemini_cli`, все с `attempt=1`, без `retryAt`; 16 остановок через 125.16–126.91 секунды, одна через 146.50 секунды. Автоматических `retry` нет. В сохранённой сессии прямо записано: «Gemini: Локальный CLI не ответил вовремя. Запрос остановлен; можно повторить ход.»

Постоянный журнал пока объединяет все ошибки Gemini в `gemini_cli`: по нему нельзя доказать подтип каждого отдельного события или причину отклонения одной длительности до 146.50 с. Однако код, повторяемая длительность и последняя сохранённая причина подтверждают основной дефект. Не требуется гипотеза о двухминутном сетевом ограничении провайдера.

Границы вывода: проблема 120/125 секунд подтверждена для текущего пути Gemini/Argon через CLI. Она не доказана для всех LLM. Ранее сохранённая диагностика DeepSeek (`tasks/deepseek-live-result.json`) содержит обработанный ответ через 226 секунд, завершившийся лимитом токенов. Это отдельная причина, которую увеличение времени не устраняет.

## Целевое поведение

- Один бюджет попытки хода: 600 секунд от начала запроса. Подготовка и вызов входят в общий срок; внутренние операции получают оставшееся время. Отсчёт экрана и отмена используют один монотонный срок. Не вводить скрытый лимит 120 секунд.
- Временный тайм-аут Gemini запускает повтор без клика пользователя. Сохранить ограничение: максимум три попытки в серии, задержки 3 и 6 секунд; после третьего сбоя — явная ручная пауза с причиной и номером попытки. «Повторить» начинает новую серию.
- Ошибки входа, недоступной модели, квоты, инструментов, настроек и обрезания не превращать в бесконечные запросы. Не считать неизвестный `.execution` автоматически временным: нужны отдельные доказанные категории.
- «Автоповтор через N с» показывается только при существующем расписании. «Повторяем запрос» — только после фактического запуска. Ручная пауза явно сообщает, какое действие необходимо.
- Любая ошибка сохраняет доску, принятые заметки, счёт и PGN `*`. Мат/пат — единственные результаты. Отменённые и поздние ответы не принимаются.

## Порядок работ

### 1. Общий срок попытки — P0

Задать контекст срока запроса, доступный движку и транспортам, с внедряемыми часами для тестов. На его основе считать внешний deadline, оставшееся время и таймер экрана. Различать время запроса и подготовку озвучки после получения хода; подготовка не должна выглядеть как ожидание LLM.

Файлы (до 5): `Chat.swift`, `RequestDeadline.swift`, `MatchEngine.swift`, новый `RequestTimingTests.swift`, `MatchTests.swift`.

Приёмка: один срок 600 с для хода; ответ до срока допустим, после срока игнорируется; изменение роли/бюджета не рассинхронизирует экран и deadline. Проверка: виртуальные часы, границы срока, отмена и поздний ответ. Зависимости: нет.

### 2. Передача срока транспортам — P0

Сначала Gemini: заменить 120/125 оставшимся бюджетом, учесть проверку CLI перед запуском, убрать внутренний повтор генерации из транспорта. Проверки версии/каталога оставить с собственными короткими ограничениями. В рамках аудита согласовать также HTTP/DeepSeek/Anthropic, ChatGPT и Claude CLI: не выводить срок из `effort`; отдельно учесть заданное время поиска LC0.

Разбить на небольшие подзадачи:

- 2a: `GeminiCLI.swift`, `GeminiCLITests.swift`, при необходимости `LocalCLIProcess.swift` (3 файла).
- 2b: `Chat.swift`, `DeepSeekTransport.swift`, `AnthropicTransport.swift`, `PlayerTests.swift`, `DeepSeekTests.swift` (5 файлов).
- 2c: `ChatGPTTransport.swift`, `ClaudeCLI.swift`, `ClaudeCLITests.swift`, `PlayerTests.swift` (4 файла).

Приёмка: fake CLI получает фактический бюджет; легальный ответ после прежней границы 120 с принимается; отмена завершает группу процессов; один вызов движка создаёт одну попытку генерации. Проверка: локальные фикстуры/HTTP-стенд, сокращённые бюджеты для быстрых тестов и один локальный сценарий >120 с без обращения к провайдеру. Зависимость: 1.

Контрольная точка A: согласованные тайм-ауты проходят тесты, существующие проверки безопасности CLI и отмены сохранены.

### 3. Повторы по причине ошибки — P0

Заменить правило «любой CLI-сбой требует пользователя» явной таблицей. Тайм-аут Gemini/Claude и подтверждённые временные сетевые сбои — ограниченный автоповтор; ошибки доступа/конфигурации — ручная пауза. Счётчик и задержки принадлежат движку. Перед запуском проверять остановку, актуальность позиции/поколения и отсутствие другого активного запроса.

Файлы: `Chat.swift`, `MatchEngine.swift`, `MatchTests.swift`, `ClaudeProviderTests.swift` (4 файла).

Приёмка: последовательность timeout → запрос 2 → легальный ответ проходит без пользовательского действия; три тайм-аута дают явную паузу; остановка или ручной повтор во время задержки не создают дубликат. ## Проверочные сценарии

1. Локальный Gemini-стенд возвращает легальный ответ через 130 с при бюджете 600 с: ход принят один раз, таймер не обрывается на 120/125 с.
2. Тот же стенд с коротким внедрённым бюджетом: первая попытка истекла, через 3 с вторая запускается сама и делает ход.
3. Три тайм-аута: задержки 3/6 с, затем ручная пауза без надписи автоповтора, результат отсутствует.
4. Ошибка входа/квоты: понятная ручная пауза без автоматической серии.
5. Стоп, повтор вручную и поздний ответ: нет параллельного запроса, лишнего хода, изменения заметок или очков.
6. Мат/пат после восстановления запроса: результат начисляется ровно один раз.

На этапе составления этого плана код приложения, исполняемый bundle и сохранённая партия не изменялись. Новых запросов к LLM не отправлялось. Выводы основаны на текущих исходниках, постоянном журнале и сохранённой сессии; новый прогон тестов для ещё не реализованных изменений не выполнялся.
